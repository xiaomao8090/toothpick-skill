# README 与思维导图

适用：项目的 README、GitHub 首页、文档首页，以及放在 README 里的思维导图、结构图、流程图。

README 属于"说服 + 阅读"：先在几秒内让人明白这是什么、值不值得用，再让人能顺利装上、用起来。

---

## 一、读者只给你几秒钟

打开 README 的人，几秒内要得到三个答案：**这是什么、对我有什么用、凭什么信它。**

所以第一屏只放三样东西：
1. **名字**
2. **一句话说明**：具体到读者能判断"我需不需要"。❌"一个强大的设计工具" ✅"让 AI 做界面时认出 AI 味的 skill"
3. **一张证据图**：
   - 效果类项目（设计、图片、排版）：同一输入的前后对比
   - 工具类项目（命令行、库）：一次真实运行的截图或 3 到 8 秒的动图
   - 界面类项目：产品界面截图

图下面用一两句话说明图里是什么，不要让读者猜。

## 二、按读者的问题排顺序

读者心里的问题依次是：
1. 这是什么？（第一屏）
2. 和别的同类项目有什么不同？
3. 怎么装？
4. 怎么用？它是怎么工作的？（适合放思维导图或流程图）
5. 有没有证据？（示例、对比、数据）
6. 有什么限制？
7. 文件结构、怎么贡献、参考来源、许可证

README 的章节按这个顺序排，而不是按项目的目录结构排。文件结构这类内部信息放后面。

## 三、让人扫得懂

- **标题写结论**："不提供风格库"，而不是"特点"
- **每段第一句加粗**，只读粗体也能看懂大意
- **会被对比的内容用表格**：不同平台的安装方式、版本对比、参数说明
- **代码块可以直接复制运行**，不要在命令里夹说明文字
- **很长的内容折叠起来**：完整清单、FAQ、更新记录放进 `<details>`，主线保持短

## 四、可信度来自真实的东西

- **徽章只放真实的**：许可证、版本号、构建状态。没有就不放
- **不编造**：星数、下载量、"被 1000+ 团队使用"、用户评价、公司 logo 墙
- **写"局限"一节**：主动说清楚哪里不行、什么情况下不适用，最好举一个真实的例子
- **写参考来源**：借鉴了哪些项目、哪些没采用以及原因
- **示例要能复现**：给出示例文件的路径，读者可以自己打开看

## 五、README 的 AI 味

| 表现 | 为什么像 AI | 什么时候可以用 |
|---|---|---|
| 每个标题前面一个 emoji：🚀 快速开始、✨ 特性、📦 安装 | 模板化，emoji 不传达信息 | 项目本身是轻松的社区项目，并且全文风格一致 |
| 一排花花绿绿的徽章 | 用数量假装活跃 | 每个徽章都是读者真的会看的信息 |
| "Features" 列表，每条都是"强大""灵活""易用" | 空话，换个项目也成立 | 每条都写具体做到了什么 |
| 居中的大 logo 加口号，下面才开始讲是什么 | 第一屏没有回答"这是什么" | 已经很有名、读者早就知道是什么的项目 |
| 结尾"⭐ 喜欢就给个 Star 吧" | 套话 | 不需要 |
| 把所有章节都塞进目录，目录比内容还长 | 读者要翻很久才看到重点 | 文档型的长 README，目录确实有用 |

## 六、GitHub 上的做工细节

- **深色模式换图**：用 `<picture>`，读者的 GitHub 是深色主题时自动显示深色版
  ```html
  <picture>
    <source media="(prefers-color-scheme: dark)" srcset="docs/mindmap-dark.png">
    <img alt="说明这张图是什么" src="docs/mindmap-light.png">
  </picture>
  ```
- **每张图都写 `alt`**：图片加载失败或者用读屏软件时，读者也知道这里是什么
- **图片清晰**：按 2 倍分辨率导出，单张控制在几百 KB 以内
- **动图**：GitHub 支持直接拖入视频，比 GIF 清晰得多、体积也小；用 GIF 时控制在 8 秒以内，第一帧就要能看懂
- **截图用真实内容**：不用 lorem ipsum，不用"示例项目 1、示例项目 2"
- **相对路径引用图片**：放在仓库里的 `docs/` 等目录，不依赖外部图床
- **中文 README**：中英文之间加空格，用全角标点

## 七、双语和多语言 README

- **一种语言一个文件**：`README.md` 是默认版本（面向国际的项目通常用英文），旁边放 `README.zh-CN.md` 等
- **每个版本第一行放语言切换**，比如 `English | 简体中文`：当前语言用纯文字，其他语言做成链接
- **各版本保持同步**：章节相同、顺序相同；改了一个，同一次提交里把其他版本也改掉
- **带文字的图片要分语言**：思维导图、结构图里有文字时，每种语言各出一版（再分浅色、深色）
- **不要逐字机翻**：标题和示例按各自语言的习惯重写；代码、命令、文件名保持完全一致

## 八、思维导图

README 里的思维导图用来回答"这个项目由哪几部分组成、它是怎么工作的"。它是一张说明图，不是装饰。

### 先决定要不要画
- 项目只有两三个部分 → 一段话或一个列表就够了，不用画
- 部分之间有先后顺序 → 画流程图，不画思维导图
- 有多个并列的组成部分，每部分下面还有内容 → 适合思维导图

### 结构
- **中心**：项目名加一句话说明它做什么
- **分支 4 到 7 个**。多了一眼看不完，少了不如用列表
- **每个分支 2 到 7 个叶子**
- **叶子写具体内容**：主词加一行灰色小字说明，比如"老套路：渐变、emoji 图标、卡片套件"，不要只写"老套路"
- **两侧分工**：左右各放一类，比如左边讲"是什么"，右边讲"怎么用"
- **只有真正的步骤才编号**

### 视觉
| 常见的 AI 做法 | 改成 |
|---|---|
| 每个分支一种颜色，彩虹色 | 黑白灰为主，只给最重要的一个分支用一个强调色 |
| 每个节点前面一个 emoji | 不加图标，靠字号和粗细分层 |
| 所有节点一样大 | 中心最重（深色块），分支名大号粗体，叶子小字浅底 |
| 连线粗、颜色深、带箭头 | 细的浅灰曲线，强调分支的线用强调色 |
| 节点挤在一起，文字被截断 | 叶子文字不换行，分支之间留足间距 |

- **同时出浅色和深色两版**，用 `<picture>` 放进 README
- **尺寸**：宽 1600px 左右设计，按 2 倍导出；GitHub 正文区大约 900px 宽，缩小后叶子文字也要能读清
- **保留源文件**：导图用 HTML 或 SVG 画，源文件放进仓库，比如 `docs/mindmap.html`，以后改内容不用重画
- **Mermaid 也可以**：GitHub 直接支持 `mindmap` 语法，改起来最方便，但默认配色是彩虹色、样式不好控制，适合内部文档；对外展示的 README 建议用自己画的图

### 放在 README 的哪里
放在"它是怎么工作的"一节开头，在读者已经知道"这是什么"之后。不要放在第一屏：第一屏的位置留给证据图。

## 自检
- 只看第一屏，一个从没听说过这个项目的人能说出它是干什么的吗？
- 只读粗体和标题，能看懂整篇的意思吗？
- 有没有编造的数字、徽章、评价？
- 有没有"局限"一节？
- 图片在深色主题下正常吗？都有 alt 吗？
- 思维导图缩小到 900px 宽时，叶子文字还读得清吗？
- 多语言 README：每个版本都有语言切换吗？章节同步吗？
