What users see
Checkout times out, payment callbacks fail, the support phones start ringing

Each square is 10 blocked requests, assuming about 70 reads and writes a second on orders.

Before a migration runs, tern works out which lock each statement takes and how long it blocks, and suggests a rewrite that does not lock the table. Open source, for PostgreSQL 12 to 17.

brew install tern-db/tap/tern

The default gen_random_uuid() is different for every row, so PostgreSQL has to rewrite the whole table. Rewrite 0042_add_public_id.sql as the six steps below; tern fix 0042 generates them for you:


ALTER TABLE orders ADD COLUMN public_id uuid;                          -- schema only, about 20 ms
ALTER TABLE orders ALTER COLUMN public_id SET DEFAULT gen_random_uuid(); -- new rows get a value
UPDATE orders SET public_id = gen_random_uuid()
  WHERE id BETWEEN $1 AND $2 AND public_id IS NULL;                    -- 10,000 rows per batch, 822 batches, blocks nothing
ALTER TABLE orders ADD CONSTRAINT public_id_nn
  CHECK (public_id IS NOT NULL) NOT VALID;                             -- no scan, about 10 ms
ALTER TABLE orders VALIDATE CONSTRAINT public_id_nn;                   -- full scan, blocks nothing
ALTER TABLE orders ALTER COLUMN public_id SET NOT NULL;                -- PostgreSQL 12+ uses the constraint to skip the scan

        

      

    

  


  

    

      

        
PostgreSQL has 8 table locks; only some of them block your users

        
The first thing tern does is label every statement with the lock it takes. Keep this table handy.

"Blocks reads and writes" means blocking ordinary SELECT and INSERT / UPDATE / DELETE. How quickly a lock is granted also depends on long-running transactions on the table; tern checks those too.

    

  


  

    

      

        
Add it to an existing project without changing a migration file

        
Works with SQL from Flyway, golang-migrate, Prisma and Rails.

      

      
    
        
  1. Install (macOS / Linux), or use the Docker image
    brew install tern-db/tap/tern
docker run --rm ghcr.io/tern-db/tern:0.9 --help
    2. 
        
  2. Create a config in the project root, pointing to your migrations
    tern init --migrations ./db/migrations
    3. 
        
  3. Connect a read-only replica and run the first analysis
    export TERN_DSN="postgres://readonly@replica:5432/shop"
tern plan
    4. 
        
  4. Add it to CI to block merges over the limit
    # .github/workflows/migrate.yml
- run: tern plan --max-lock 2s --format github
    5. 
      

      
Not supported yet: MySQL and SQLite (MySQL is planned), DDL inside stored procedures, running natively on Windows (use WSL or Docker).
